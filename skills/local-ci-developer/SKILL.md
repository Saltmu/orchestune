# Local CI & TDD Developer Skill

本スキルは、開発における設計プラン作成から、GitHub上でのIssue起票、テスト駆動開発（TDD）による実装、プッシュ前のローカルでの統合CI検証、PR（Pull Request）作成、およびIssueの自動クローズにいたるまでの一連の標準開発ワークフローと品質管理手順を定めたものです。

## 適用トリガー
ソースコードの編集、テストの作成・実行、リファクタリング、Gitへのコミット/プッシュ操作など、コードの変更作業を伴うすべての開発タスクの際に必ずロードして実行してください。

## ワークフロー

### 0. 着手前の要件充足チェック（対応不要スキップ機構）
- 実装プランを作る前に、対象Issueの要件が既に`main`へ実装済みでないかを確認します（他のサブタスクが依存関係の都合で重複して実装してしまっている場合等）。
- **既に要件を満たしていることを確認できた場合**は、コミット・PRの作成は行わず、以下のみを行って作業を終了してよいものとします（Issueのクローズ・依存関係の解決・quotaの解放はOrchestune dispatcher側が自動的に決定論的に行うため、それ以上の対応や人間の判断待ちは不要です）。
  1. Issueへ、要件が既に満たされている根拠（実装済みのコミット/ファイル、該当テストが通過していること等）をコメントする。
  2. `status:in-progress` ラベルを外し、`status:not-needed` ラベルを付与する。
- コミットもPRの作成もしないため、通常の完了検知（PRの存在をシグナルとする仕組み）では永遠に完了と判定されません。`status:not-needed`ラベルの付与自体が完了シグナルになるため、これを忘れずに行ってください。

### 1. 設計・実装プラン作成
- 変更を伴うタスクの開始前に、必ず `planning_mode` に従い `implementation_plan.md` を作成します。
- 実装アプローチや影響範囲、オープンな疑問点をまとめ、必ずユーザーの承認を得てから実装フェーズへ進みます。
- **例外（非対話型の自動実行時）**: タスクの起動プロンプトで「非対話型のバックグラウンド自動実行」であることが明示されている場合（`orchestune-dispatch` からの起動等）、標準入力への応答は得られないため、承認待ちで停止してはいけません。`implementation_plan.md` の作成まで完了した時点で、その内容に基づき自らの判断で実装フェーズへ直ちに進んでください。

### 2. GitHub Issueの起票
- プランが承認された段階で、GitHub上でIssueを起票します。環境に応じて、以下のいずれかの手段を用いてください。
  - **手段A: GitHub CLI (推奨)**
    `gh` コマンドを使用して起票します。
    ```bash
    gh issue create --title "Issueのタイトル" --body-file .github/issue_template.md
    ```
  - **手段B: GitHub MCP (MCP利用可能な環境)**
    GitHub MCPサーバーの `create_issue` ツールを呼び出します。引数には、タイトルと `.github/issue_template.md` の内容に沿って記述した本文を指定します。
  - **手段C: Web UI (Web/手動環境)**
    ブラウザでGitHubのリポジトリにアクセスし、`.github/issue_template.md` の内容をコピー＆ペーストして手動でIssueを作成します。
- 起票したIssue番号（例: `#123`）を記録しておきます。
- バグ修正Issueの場合は、Issue本文の「再現手順 (Reproduction)」欄（テンプレート参照）に、再現条件・再現コマンド・期待される結果と実際の結果を記載します。

### 3. Reproducer Step（再現手順の確立）
- バグ修正Issueでは、実装に着手する前に、Issueに書かれた症状を**そのまま**再現する最小限のテスト（`tests/`ディレクトリ配下）またはスクリプトを書きます。
- `poetry run pytest` を実行し、Issue記載の症状通りに実際に失敗する（Red）ことを確認します。単に何らかのアサーションが落ちるだけでなく、報告された症状と一致していることを確認してください。
- このテストが、次のテストファーストステップ以降の起点になります。
- 再現すべき不具合が存在しない新規機能Issueの場合は、本ステップを「該当なし」としてスキップし、次のステップへ進んでよいものとします。

### 4. Baseline-aware Test Evaluationの準備（ベースライン取得）
- 実装に着手する**前**に、変更前のコードで `poetry run pytest -n auto --tb=no -q` を実行し、既に失敗しているテスト（今回のIssueとは無関係な既存の不具合やflaky test）の一覧を控えておきます。作業メモ等への一時的な記録で構いません（コミット不要）。
- この記録は、ステップ9（ローカルCI）で「今回の変更によって新規に失敗するようになったテストがないか」を判定する基準として使用します。

### 5. 実装前のテスト作成 (テストファースト)
- ステップ3で作成したReproducerのテストを土台に、実装を開始する前に、まず `tests/` ディレクトリ配下に、新規機能や改修仕様（正常系の主要シナリオ）を満たすテストケースを先に記述します。
- この段階で `poetry run pytest` を実行し、追加したテストが期待通り失敗（Red）することを確認します。

### 6. 機能の実装とテスト通過
- テストをパスさせるために必要なコードを実装します。
- `poetry run pytest` を実行し、すべてのテストがパス（Green）することを確認します。
- ステップ3のReproducerや本ステップの追加テストが実装後も失敗し続ける場合は、次の「7. Failure Analyst」の手順に従います。

### 7. Failure Analyst（連続失敗時の根本原因分析）
- 同一の失敗（Reproducerのテスト、またはステップ9のローカルCI）が**2回以上連続**で解消しない場合、闇雲に再修正を試みる前に一度立ち止まり、以下を明文化します。
  1. 失敗の直接原因（スタックトレース・diffの該当箇所）
  2. 想定した修正で解消されなかった理由の仮説
  3. 次に試す具体的な修正方針
- 3回分析しても解消しない場合は、それ以上の自動再試行を打ち切り、Issueにここまでの調査内容をコメントして人間の判断を仰ぎます（Orchestune dispatcherの`force-serial`フォールバックと同じく、無限ループを避けて人間にエスカレーションする考え方です）。

### 8. エッジケースと異常系のカバレッジ補強
- カバレッジが **75%** に満たない場合や、品質向上のため、エッジケースやエラーハンドリング（異常系）のテストを追加で記述し、カバレッジを向上させます。
- カバレッジ計測は開発ループを軽くするため `pytest` の既定（`addopts`）には含まれていません。未カバーの行を確認する際は `poetry run pytest --cov=orchestune --cov-branch --cov-report=term-missing` のように明示的にオプションを指定して実行してください（Windows用の`.\scripts\local-ci.ps1`とLinux/macOS用の`./scripts/local-ci.sh`はこのオプションを常に付与して実行します）。

### 9. ローカルCIの一括実行とエラー解消
コードの修正が完了したら、実行OSを判定し、対応するコマンドをプロジェクトルートで実行します。

Windows PowerShell:

```powershell
.\scripts\local-ci.ps1
```

Linux / macOS:

```bash
./scripts/local-ci.sh
```

どちらのスクリプトも以下の順にチェックを行います。失敗した場合はそれぞれのステップに応じてエラーを解消してください。

#### ① Ruff Format/Lint エラーの場合
- 自動フォーマットを実行: `poetry run ruff format`
- 自動Lint修正を実行: `poetry run ruff check --fix`
- 自動修正できなかったエラーは手動で修正します。

#### ② Mypy 型チェックエラーの場合
- 型注釈（Type Hints）の不整合を確認します。
- 必要に応じて、`# type: ignore` は最終手段とし、可能な限り正しい型を定義してください。

#### ③ Pytest テスト失敗の場合
- テストコード、または実装コードのバグを特定し、修正します。同一の失敗が2回以上連続する場合は「7. Failure Analyst」の手順に従います。
- カバレッジが75%に達していない場合は、不足しているテストを追加します。
- **合格基準はBaseline-aware（ベースライン相対）で判定します**: 「全テストgreen」を機械的な基準にするのではなく、ステップ4で記録したベースラインと比較して**新規に失敗するようになったテストがないこと**、かつ**ステップ3のReproducerテストがfail→passに転じていること**を基準とします。ベースライン由来の既存失敗が残っている場合はブロッカーとせず、PR本文の「ベースライン差分」欄にその旨を記載します。

#### ④ Detect Bloat 警告の場合
- ファイルやスキルのサイズが肥大化（目安としてコード: 1,000行以上、スキル: 500行以上）していたり、複雑度が高すぎる警告（`poetry run detect-bloat`等）を検知した場合は、そのままコード修正を進めずに作業を一時停止し、まずユーザーにモジュールやプロンプトの分割リファクタリング計画を提示し、承認を得てください。

### 10. すべてがパスした後の確認とPR作成（PR agent / finalization）
- OSに対応するローカルCIスクリプト（Windowsでは`.\scripts\local-ci.ps1`、Linux/macOSでは`./scripts/local-ci.sh`）が `✨ Local CI passed successfully!` と出力して正常終了したことを確認します。
- `walkthrough.md` を作成し、実施した変更やテスト内容、Local CI の結果をまとめます。
- PR本文は、必ずリポジトリのPRテンプレート（`.github/pull_request_template.md`）から作成します。テンプレートを直接`--body-file`へ渡さず、作業用ファイル（例: `/tmp/pr_body.md`）へコピーしてから、見出し・チェックリスト・必須項目を削除せずにすべて記入してください。
- テンプレートにプレースホルダー、未記入の箇条書き、未判定のチェックボックスが残っていないことを確認します。該当しない項目は削除せず、理由を添えて「該当なし」と記載します。
- GitHub上にPRを作成します。変更内容（Walkthrough）やローカルCIの合格有無、関連するIssue番号（`Closes #<Issue番号>`）に加え、以下をテンプレートの対応する欄へ記述してPRを送信します。
  - **再現手順と修正確認**: ステップ3のReproducerテスト/スクリプトが、修正前はIssue記載の症状通りに失敗し、修正後にパスすることを確認した旨（新規機能の場合は「該当なし」）。
  - **ベースライン差分**: ステップ4のベースラインと比較して新規のリグレッションがないこと、既存の未解決failureがあれば一覧。
  環境に応じて、以下のいずれかの手段を用いてください。
  - **手段A: GitHub CLI (推奨)**
    `gh` コマンドを使用し、記入・確認済みの作業用PR本文からPRを作成します。
    ```bash
    cp .github/pull_request_template.md /tmp/pr_body.md
    # /tmp/pr_body.md の全項目を記入し、未記入箇所がないことを確認する
    gh pr create --title "PRのタイトル" --body-file /tmp/pr_body.md
    ```
  - **手段B: GitHub MCP (MCP利用可能な環境)**
    `.github/pull_request_template.md`を読み込み、その構造と全項目を維持して記入した本文をGitHub MCPサーバーの `create_pull_request` ツールなどへ渡します。
  - **手段C: Web UI (Web/手動環境)**
    作業ブランチをリモートにプッシュし（`git push origin <branch-name>`）、ブラウザでGitHubのリポジトリにアクセスし、自動表示されたPRテンプレートの全項目を記入してPull Requestを作成します。
- PR作成後、次のステップ11のLLMレビュー工程へ進みます。

### 11. LLMによる自動PRレビューと指摘対応サイクル（クロスモデルレビュー）
PR作成後、客観的な品質担保と多角的な検証のため、実装エージェントとは異なるモデル（クロスモデル）によるLLM自動PRレビューを実施し、指摘事項の解消まで自律的な改善サイクルを回します。

#### ① レビュー依頼先モデルの確認（ユーザー問い合わせ / クロスモデルの原則）
- **対話モード時**: PR作成直後に、レビューを依頼するLLM（`claude` または `codex`、あるいはスキップ）をユーザーへ問い合わせて決定します。
  - **クロスモデルの推奨**: 実装を担当したモデル（例: Antigravity/Gemini）とは異なるモデル（ClaudeやCodex）を選択することで、バイアスを排除した客観的で高品質なレビューが行えます。
- **非対話モード時（自動ディスパッチ等）**: 実装エージェントと異なるモデルを優先して選択するか、リポジトリの既定（例: `claude`）を自動実行します。

#### ② レビュー依頼の実行と待機（単一統合コマンドの実行）
- 決定したモデルに応じて、以下の単一コマンドを同期的に実行します。`wait_for_review.py` が**レビュー依頼コメントの投稿・完了待機・指摘解析サマリーの出力**までを1ステップで自動完結します。
  - **注意（2重送信防止）**: コマンド自体がコメント投稿を行うため、事前に `gh pr comment` を別個に手動実行してはなりません。
  ```bash
  # Claudeに依頼する場合（コメント投稿 + 待機 + 解析）
  poetry run python scripts/wait_for_review.py --pr <PR番号> --bot-name claude

  # Codexに依頼する場合（コメント投稿 + 待機 + 解析）
  poetry run python scripts/wait_for_review.py --pr <PR番号> --bot-name codex
  ```

#### ③ レビュー結果の確認と無応答タイムアウト処理
- スクリプトが完了すると、標準出力に `[AI Review Summary]` とレビュー本文・インライン指摘が出力されます。
- **無応答時のタイムアウト処理**:
  - `wait_for_review.py`（既定タイムアウト: 10分）がタイムアウトで失敗した場合、再依頼コマンドを**1回のみ再実行**（`--timeout 300`）します。
  - それでも応答がない場合（Actions未設定、メンション未認識、外部サービス障害等）は、待機を打ち切ります。
    - **対話モード時**: ユーザーにレビュー応答が得られなかった旨を報告し、再試行するかLLMレビューをスキップして手動レビューへ進むかを問い合わせます。
    - **非対話モード時**: ジョブの無限停止を防ぐため、PRコメントに無応答の状況を記録した上で、Issueラベルを `status:blocked-human-review` へ変更して安全にエスカレーションします。

#### ④ 指摘内容の厳格な合否判定とコード修正
- レビュー結果から指摘の有無を厳密に判定します。
  - ❌ **誤判定の禁止事項**:
    - レビュアーの自己タスク進捗チェックリスト（`- [x] Gather context...` や `- [x] Post findings` 等）をPRの合格と誤認することを禁止。
    - PRレビューのステータスが `COMMENTED` であること（`CHANGES_REQUESTED` ではないこと）をもって指摘なしとみなすことを禁止（ボットActionは通常 `COMMENTED` として投稿します）。
    - 「Minor observations」や「Non-blocking」であっても、修正すべき内容が含まれている場合は放置せず精査すること。
  - ⭕ **「指摘あり」と判定すべき基準**:
    - `[AI Review Summary]` の Status が `FINDINGS_DETECTED` の場合。
    - レビュー本文またはインラインコメントに `### Findings`、`🔴`、`⚠️`、`Bug:`、`Critical:`、`Issue:`、`Still open`、`P1`/`P2`/`P3` 等の指摘項目が1件でも記載されている場合。
- **指摘への対応**:
  - **妥当な指摘の場合**:
    - 指摘に合わせて実装コードやテストコードを修正します。
    - OSに対応するローカルCIスクリプト（Windowsでは`.\scripts\local-ci.ps1`、Linux/macOSでは`./scripts/local-ci.sh`）を実行し、エラーがゼロであることを確認します。
    - 変更をコミットし、PRブランチへプッシュします（`git push origin <ブランチ名>`）。
  - **妥当でない指摘（誤認・仕様上意図した設計など）の場合**:
    - 修正は行わず、なぜ現状の設計が正しいのか、技術的・仕様的な根拠を整理します。

#### ⑤ 対応結果の返信コメント投稿と再レビュー依頼 (必須)
- 修正コミットをプッシュした後、作業用ファイル（例: `/tmp/review_reply.md`）に対応内容を記述し、`wait_for_review.py` の `--body-file` オプション経由で再レビューをトリガー・待機します。
- **重要**: `gh pr comment` を別個に手動実行することは二重送信の原因となるため厳禁です。必ず `--body-file` を通じて単一コマンドで実行してください。
- 返信ファイル（`/tmp/review_reply.md`）の記載フォーマット：
  ```markdown
  ## レビュー指摘への対応 (Round 1/5)

  ### 対応内容
  - [対応] レビュー応答無応答時のタイムアウト（10分/最大20回ポーリング）およびエスカレーション手順を追加しました（コミット: abc1234, scripts/wait_for_review.py）
  - [対応] 修正コミット後のPRへの対応返信コメント投稿を必須化しました（コミット: abc1234）
  - [見送り] △△については、XXXの仕様に基づく意図した動作のため現状維持とします（理由: ...）。

  @claude review
  ```
- 再レビュー実行コマンド：
  ```bash
  poetry run python scripts/wait_for_review.py --pr <PR番号> --bot-name claude --body-file /tmp/review_reply.md
  ```

#### ⑥ 終了条件とループ制御（セーフティガード）
- **終了条件**: `[AI Review Summary]` の Status が `ALL_CLEAR` となり、レビュアーから新たな未解消指摘がない状態（LGTM / All checks passed / 指摘ゼロ）になった場合のみ、レビューサイクルを完了とし、次のステップへ進みます。
- **ループ上限（デフォルト5回）と永続的カウント**:
  - 指摘対応と再レビューの反復は**最大5回**までとします。
  - セッション中断や再開があった場合でも、PRコメント内の `@claude review` / `@codex review` 投稿履歴や `Round X/5` 表記から累積回数を算出します。
  - 5回反復しても指摘が解消しない、または見解の相違が平行線をたどる場合は、自動反復を停止します。
  - これまでの議論の論点と対応状況をPRコメントに整理した上で、人間のレビュー（`status:blocked-human-review` または人間のレビュアーによる判断）へエスカレーションします。

### 12. PRマージとIssueの自動クローズ
- **`orchestune-dispatch`から`--parent-issue`付きで起動された場合**: 実際のコード統合とクローズは、ここで作成した個別PRが人間にマージされることではなく、Integratorのパイプラインが担います。Integratorは`status:done`ラベル付与後に子ブランチを検知し、CI通過後に親ブランチへ自動マージし、対象Issueを自動的にクローズします。ここで作成した個別PRはレビュー用の記録として残り、必ずしも人間がマージする必要はありません（マージ済み内容が親ブランチに既に取り込まれていれば、そのままクローズして構いません）。
- **上記以外（対話的にこのスキル単体を使う場合等）**: 従来通り、ユーザーによるPRレビューおよびマージを待ち、PRがマージされたら関連するGitHub Issueが自動的にクローズされたことを確認します。
