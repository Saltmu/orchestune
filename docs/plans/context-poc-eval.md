### 比較条件の差・制約・欠測ポリシー
- **モデル選択・推論設定の記録と制約**: 当初 `claude` CLI を試行したが OAuth セッション期限切れ（`authentication_failed`）のため、同一環境で利用可能な `codex-cli 0.169.0` へ切り替え、全 5 タスク × 3 条件（計 15 試行、ログ再利用した `#1858` の 3 試行も同一セッション・同一 `run_live_eval.py` 実行による）を同一の設定（Codex ユーザー設定 `config.toml` の `model = "gpt-6.1-sol"`, `model_reasoning_effort = "high"`）および同一サンドボックス設定で揃えた。なお `codex exec --json` のイベント（`thread.started` / `turn.completed`）は実行時の解決済みモデル ID 文字列を出力しないため、設定ファイル上の固定値として記録する。
- **トークンとバイト数の分離**: `injected_bytes` はプロンプト／`context.json` の UTF-8 バイト数であり、`input_tokens` / `output_tokens` / `total_tokens` / `cost_usd` の代理指標としては扱わない。
- **欠測理由**:
  - `cost_usd`: `codex exec --json` が課金額を出力しないため全試行で `null`（理由: `codex exec --json does not emit cost_usd`）。
  - 手戻り（再レビュー回数・fix 回数）および実装 CI 成否: 本評価は同一 `base_sha` 上での read-only 技術計画生成タスクとして実施したため `null`（理由: `read-only planning evaluation on merged base_sha; no PR/CI rework loop executed`）。
  - `#1858` の一部 `wall_ms`: 初回実行ログをキャッシュ再利用したため `run_live_eval.py` 集計上 `null`（初回ログ出力の実測値は `baseline: 77,367.20 ms`、`tier1_only: 61,134.61 ms`、`tier1_plus_tier2: 62,224.92 ms`）。

### 実行前に定めた継続・見直し基準
1. **品質基準**: `tier1_only` および `tier1_plus_tier2` で Tier 1 必須入力（目的・受入条件・依存先確定成果）の欠落がなく、計画の受入条件・依存制約の網羅性が `baseline` 以上であること。
2. **費用・遅延基準**: `tier1_plus_tier2`（または `tier1_only`）の `input_tokens` が `baseline` 以下（または削減効果が後続参照・探索回数の減少と両立）であり、かつコンテキスト構成レイテンシが 1 起動あたり 10 秒以下であること。
3. **判断規則**: 必須契約の欠落や品質低下が生じる場合は「再設計」または「見送り」、Tier 1 が品質・トークン双方で優位かつ Tier 2 の課題が局所的改善で解消可能なら「継続（改善項目付き）」とする。

### 実測からの分析
1. **Tier 1 の一貫した削減効果**: `tier1_only` は 5 タスクすべてで `baseline` より大幅に `input_tokens` を削減した（`-25.2%`〜`-53.5%`、合計 `-39.3%`）。`baseline` では Issue の要件・制約を特定するために複数回の `rg`/`sed` 探索を要したのに対し、`tier1_only` では `.eval-context.json` の 1〜2 回の読取で要件と依存契約を即座に把握できた。
2. **Tier 2 BM25 の二面性**: `tier1_plus_tier2` は全体では `baseline` 比 `-28.1%` を達成したが、`tier1_only` 比では `+18.4%` トークンが増加し、`#1852` 単体では `baseline` 比 `+14.7%`（リポジトリ読取 `16` 回 vs `baseline` `5` 回）となった。関連度の低い過去ヒット（例: `#1852` に対する `#1270` 等）が追加探索を誘発したためである。
3. **後続 `gh` 取得が 0 回となった理由**: 本評価では `base_sha` 上に既に該当機能・テストが存在したため、`baseline` 側も `gh` ではなくローカル `rg`/`sed` で仕様を逆探索した。未実装の新規タスクでは `baseline` の `gh` 取得や手戻りがさらに増える可能性が高い。

## 4. 継続判断（Continue / Redesign / Drop）

**判断: 継続（条件付き・Tier 1 を主軸とし、Tier 2 は限定改善の上で段階適用する）**

| 基準 | 実測結果 | 判定 |
| --- | --- | --- |
| 品質（必須入力・網羅性） | 全 15 試行で計画品質は `baseline` 同等以上。ただし `#1866` で受入見出し不一致による空抽出を確認 | 条件付き合格（フォールバック改善要） |
| 費用・遅延（トークン・構成時間） | `tier1_only` で `input_tokens` **-39.3%**、`tier1_plus_tier2` で **-28.1%**。構成時間は `1.44–5.13 秒`（基準 10 秒以下） | 合格（Tier 2 過剰探索の抑制余地あり） |

### 次のアクション（#1841 統合・後続改善へ引き継ぐ事項）
1. **#1841（PR #1865）の `main` 統合を継続する**: 設計・実装（`context` 索引・構成・注入・PoC 契約）は実測上十分なトークン削減効果と安定性（`ready`・予算遵守・低遅延）を示したため、統合を進める。
2. **Tier 1 を標準注入の主軸とする**: 最も費用対効果が高く安定しているのは `tier1_only`（`-39.3%`）であるため、まずは Tier 1 の確実な注入を運用に乗せる。
3. **後続の軽量改善（3 点）**:
   - `compose_launch_context` の Tier 2 検索で対象 `issue_number` 自身を必ず除外する。
   - Issue 本文に定型見出しが無い場合（`#1866` 型）の受入条件フォールバック抽出を追加する。
   - Tier 2 BM25 の返却上限やスコア閾値（例: `k=2〜3` やスコア下限）を調整し、無関係ヒットによる探索増加を抑える。
